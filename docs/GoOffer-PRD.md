# GoOffer MVP 产品需求文档 PRD

版本：v0.1  
日期：2026-05-28  
产品阶段：MVP  
产品类型：个人求职信息整合网站  
目标用户：正在密集投递的应届生 / 社招求职者

## 1. 背景

求职者在密集投递阶段通常会同时管理多个岗位、公司、面试安排和 Offer 信息。当前常见管理方式包括 Excel、Notion、备忘录、聊天记录收藏等，但这些方式存在信息分散、状态不清晰、面试复盘难沉淀、Offer 对比不系统等问题。

GoOffer 希望为个人求职者提供一个轻量但完整的求职管理工具，覆盖从岗位筛选、投递跟进、面试记录、AI 复盘到 Offer 对比的核心流程。

## 2. 问题定义

目标用户在求职过程中面临以下问题：

1. 投递岗位数量多，岗位信息分散，难以统一管理。
2. 不同岗位处于不同流程阶段，容易忘记跟进。
3. 面试问题和回答记录零散，无法形成系统复盘。
4. 面试后不知道自己表现如何，也不知道下一轮该重点准备什么。
5. 拿到多个 Offer 后，容易只看薪资，缺少结构化对比。

## 3. 产品定位

GoOffer 是一个面向个人用户的求职流程管理网站，帮助用户管理岗位信息、跟踪投递进度、记录面试问题与回答、通过 AI 生成面试复盘，并在获得 Offer 后进行横向对比。

一句话定位：

> 从看到岗位到最终选择 Offer，GoOffer 帮你把每一步都整理清楚。

## 4. 目标用户

### 4.1 主要用户

正在密集投递岗位的应届生和社招求职者。

用户特征：

- 同时关注多个岗位。
- 面试流程较多，容易混淆进度。
- 希望提高面试表现。
- 愿意主动记录求职过程。
- 熟悉基础网页操作，不需要复杂协作功能。

### 4.2 非目标用户

MVP 阶段暂不覆盖：

- 企业招聘方。
- HR / 猎头团队。
- 多人协作求职小组。
- 希望系统自动投递或自动抓取岗位的用户。

## 5. 产品目标

1. 帮助用户统一管理投递前的岗位信息。
2. 帮助用户清晰追踪每个岗位的投递状态。
3. 帮助用户记录每轮面试的问题和回答。
4. 帮助用户通过 AI 生成结构化面试复盘。
5. 帮助用户在拿到 Offer 后进行多维度对比。
6. 验证用户是否愿意持续使用 GoOffer 管理求职流程。

## 6. 成功指标

MVP 上线后重点关注：

1. 用户注册完成率。
2. 首次创建岗位完成率。
3. 人均创建岗位数量。
4. 岗位状态更新次数。
5. 面试记录创建率。
6. AI 总结生成率。
7. Offer 对比功能使用率。
8. 7 日留存率。
9. 用户是否在多个求职阶段持续回访。

## 7. MVP 范围

### 7.1 MVP 核心流程

```text
注册 / 登录
-> 添加岗位
-> 筛选 / 排序岗位
-> 标记投递状态
-> 添加面试时间
-> 记录面试问题与回答
-> 生成 AI 面试总结
-> 添加 Offer
-> 对比 Offer
```

### 7.2 MVP 功能结构

```text
GoOffer
├── 账号系统
│   ├── 注册
│   └── 登录
│
├── 投递前
│   ├── 岗位信息
│   └── 条件筛选 / 排序
│
├── 投递中
│   ├── 投递进度
│   ├── 面试时间
│   ├── 面试回答
│   └── 面经 / AI 总结
│
└── 拿到 Offer 后
    └── Offer 对比
```

## 9. 用户流程

### 9.1 新用户流程

```text
打开 GoOffer
-> 注册账号
-> 登录
-> 进入首页
-> 查看空状态引导
-> 添加第一个岗位
-> 回到岗位列表 / 首页
```

### 9.2 投递前流程

```text
添加岗位
-> 填写岗位信息
-> 设置优先级
-> 查看岗位列表
-> 使用筛选 / 排序
-> 决定是否投递
```

### 9.3 投递中流程

```text
进入岗位详情
-> 修改投递状态
-> 添加面试时间
-> 记录面试问题
-> 填写自己的回答
-> 生成 AI 总结
-> 根据总结准备下一轮
```

### 9.4 Offer 对比流程

```text
岗位状态更新为已拿Offer
-> 添加 Offer 信息
-> 进入 Offer 对比页
-> 查看多维度评分
-> 比较不同 Offer
-> 记录最终倾向
```

## 12. 功能需求

### 12.1 账号系统

优先级：P0

需求：

- 用户可以使用用户名和密码注册。
- 用户可以使用用户名和密码登录。
- 用户登录后只能访问自己的数据。
- 未登录用户不能访问产品主页面。

### 12.2 岗位信息管理

优先级：P0

需求：

- 用户可以手动添加岗位。
- 用户可以编辑岗位信息。
- 用户可以删除岗位。
- 用户可以查看岗位详情。
- 用户可以设置岗位优先级。
- 用户可以为岗位添加标签。

### 12.3 筛选 / 排序

优先级：P0

需求：

- 用户可以按状态筛选岗位。
- 用户可以按城市筛选岗位。
- 用户可以按优先级筛选岗位。
- 用户可以按关键词搜索岗位。
- 用户可以按创建时间、更新时间、薪资、优先级排序。

### 12.4 投递进度管理

优先级：P0

需求：

- 用户可以修改岗位状态。
- 用户可以在岗位列表和岗位详情中看到当前状态。
- 状态修改后需要更新岗位更新时间。
- MVP 不强制状态按固定顺序流转。

### 12.5 面试记录

优先级：P0

需求：

- 一个岗位可以添加多轮面试。
- 一轮面试可以记录多个问题。
- 每个问题可以填写用户自己的回答。
- 面试可以记录时间、形式、面试官、会议链接和准备事项。

### 12.6 AI 面试总结

优先级：P0

需求：

- 用户可以基于某一轮面试生成 AI 总结。
- AI 总结输入包括岗位信息、面试信息、问题和回答。
- AI 输出包括复盘、优化建议、下一轮准备建议。
- 用户可以保存 AI 总结。
- AI 总结保存后展示在岗位详情中。

### 12.7 Offer 对比

优先级：P0

需求：

- 用户可以为已拿 Offer 的岗位添加 Offer 信息。
- 用户可以横向对比多个 Offer。
- 用户可以填写评分维度。
- 系统自动计算综合评分。
- 用户可以记录最终决策。

## 13. 用户故事

1. 作为求职者，我想手动添加岗位信息，以便统一保存我感兴趣的机会。
2. 作为求职者，我想筛选和排序岗位，以便优先处理最重要的岗位。
3. 作为求职者，我想更新投递状态，以便知道每个岗位当前进展。
4. 作为求职者，我想记录面试时间，以便提前准备和避免错过安排。
5. 作为求职者，我想记录面试问题和回答，以便复盘自己的表现。
6. 作为求职者，我想让 AI 总结我的面试表现，以便知道下一轮该改进什么。
7. 作为求职者，我想保存 AI 总结，以便之后回看和持续优化。
8. 作为求职者，我想录入 Offer 信息，以便把不同机会放在一起比较。
9. 作为求职者，我想看到 Offer 综合评分，以便辅助最终选择。
10. 作为未登录用户，我不能访问他人的求职数据，以便保护个人隐私。

## 14. 验收标准

### 14.1 注册 / 登录

- Given 用户输入未被占用的用户名和有效密码，When 点击注册，Then 系统创建账号并进入首页。
- Given 用户输入错误密码，When 点击登录，Then 系统提示用户名或密码错误。
- Given 用户未登录，When 访问首页，Then 系统跳转到登录页。
- Given 用户已登录，When 访问岗位列表，Then 只能看到自己的岗位。

### 14.2 岗位管理

- Given 用户在新增岗位页填写公司名称和岗位名称，When 点击保存，Then 系统创建岗位并展示在岗位列表中。
- Given 用户未填写公司名称或岗位名称，When 点击保存，Then 系统提示必填字段，且不创建岗位。
- Given 用户编辑岗位信息，When 点击保存，Then 岗位详情展示更新后的内容。
- Given 用户删除岗位，When 确认删除，Then 岗位从列表中移除。

### 14.3 筛选 / 排序

- Given 用户存在多个岗位，When 选择状态筛选，Then 列表只展示对应状态的岗位。
- Given 用户输入关键词，When 执行搜索，Then 列表展示公司名或岗位名匹配的结果。
- Given 没有符合条件的岗位，When 筛选生效，Then 页面展示无结果状态。
- Given 用户选择排序方式，When 排序生效，Then 岗位列表按对应规则排列。

### 14.4 投递进度

- Given 岗位处于“待投递”，When 用户修改为“已投递”，Then 岗位状态更新成功。
- Given 用户修改岗位状态，When 更新完成，Then 岗位更新时间同步变化。
- Given 状态更新失败，When 请求返回错误，Then 页面展示错误提示并保留原状态。

### 14.5 面试记录

- Given 用户进入岗位详情，When 添加面试记录，Then 面试记录出现在该岗位下。
- Given 用户添加多个问题，When 保存面试，Then 每个问题和回答都被保存。
- Given 面试时间为空，When 保存面试，Then 系统允许保存，但不展示在最近面试列表中。
- Given 用户删除某轮面试，When 确认删除，Then 该面试及其问题记录被移除。

### 14.6 AI 总结

- Given 某轮面试存在问题或回答，When 用户点击生成 AI 总结，Then 系统生成结构化总结。
- Given AI 正在生成，When 用户等待结果，Then 页面展示加载状态，且不能重复提交。
- Given AI 生成失败，When 请求返回错误，Then 页面展示失败提示和重试入口。
- Given AI 总结生成成功，When 用户点击保存，Then 总结展示在岗位详情中。

### 14.7 Offer 对比

- Given 岗位状态为“已拿Offer”，When 用户添加 Offer 信息，Then Offer 出现在对比页中。
- Given 用户填写评分维度，When 保存 Offer，Then 系统自动计算综合评分。
- Given 存在多个 Offer，When 用户进入 Offer 对比页，Then 系统以表格形式横向展示。
- Given 没有 Offer，When 用户进入 Offer 对比页，Then 页面展示空状态和引导文案。

## 15. 非功能需求

### 15.1 权限与隐私

- 用户必须登录后才能访问个人数据。
- 用户只能查看、创建、编辑、删除自己的数据。
- 密码必须加密存储，不允许明文保存。
- AI 总结使用的数据仅限当前用户授权输入的岗位和面试内容。

### 15.2 性能

- 常规页面首屏加载建议控制在 3 秒以内。
- 岗位列表在 500 条以内应保持可用。
- 搜索、筛选、排序应在用户操作后及时反馈。
- AI 总结生成允许较长等待，但必须展示明确加载状态。

### 15.3 可用性

- 表单必填项需要有明确提示。
- 删除操作需要二次确认。
- 空状态需要提供下一步操作入口。
- 错误状态需要提供可恢复路径，例如重试或返回。

### 15.4 兼容性

- MVP 优先支持桌面 Web。
- 需要兼容主流现代浏览器。
- 移动端需要基础可用，但不作为第一优先级深度优化。

### 15.5 可访问性

- 表单输入框需要有明确标签。
- 错误提示不能只依赖颜色。
- 关键操作需要支持键盘访问。
- 文本与背景需要满足基础对比度要求。

## 16. 数据与分析需求

建议埋点事件：

| 事件 | 说明 |
|---|---|
| user_registered | 用户注册成功 |
| user_logged_in | 用户登录成功 |
| job_created | 创建岗位 |
| job_updated | 更新岗位 |
| job_status_changed | 修改岗位状态 |
| job_filtered | 使用筛选 |
| interview_created | 创建面试记录 |
| question_created | 添加面试问题 |
| ai_summary_requested | 请求 AI 总结 |
| ai_summary_saved | 保存 AI 总结 |
| offer_created | 创建 Offer |
| offer_compared | 查看 Offer 对比 |

核心分析问题：

1. 用户是否能顺利创建第一条岗位？
2. 用户是否会持续更新岗位状态？
3. 面试记录是否是高频功能？
4. AI 总结是否带来复访？
5. Offer 对比是否在后期求职流程中被使用？

## 17. 边界情况

需要处理：

1. 首次登录无岗位。
2. 筛选结果为空。
3. 岗位被删除后，其面试和 Offer 的关联处理。
4. AI 生成失败。
5. 网络请求失败。
6. 用户重复点击保存。
7. 用户输入超长文本。
8. 用户访问不存在的岗位详情。
9. 用户访问不属于自己的数据。
10. Offer 对比少于 2 个 Offer。

## 18. 依赖

1. 云端数据库。
2. 用户认证能力。
3. AI 模型服务。
4. 前端表单和列表组件。
5. 后端接口服务。
6. 基础部署环境。

## 19. 风险与应对

### 19.1 用户记录成本过高

风险：用户不愿意手动录入太多信息。  
应对：新增岗位表单保持轻量，公司名称和岗位名称为唯一必填项。

### 19.2 AI 总结质量不稳定

风险：AI 输出泛泛而谈，用户觉得没价值。  
应对：要求 AI 输出结构化内容，并基于岗位信息、问题、回答生成具体建议。

### 19.3 Offer 评分过于主观

风险：综合评分无法真实代表用户偏好。  
应对：MVP 采用等权重平均，后续再支持自定义权重。

### 19.4 仅用户名密码导致找回困难

风险：没有邮箱或手机号时，用户忘记密码难以找回。  
应对：MVP 可暂不支持找回密码，后续扩展邮箱绑定。

### 19.5 功能范围膨胀

风险：求职管理天然容易扩展到简历、社区、插件、自动投递。  
应对：MVP 严格聚焦岗位管理、面试记录、AI 总结、Offer 对比。

## 20. 设计交接说明

设计时需要重点关注：

1. 产品应以“求职阶段”组织信息，而不是复杂后台管理系统。
2. 首页要让用户快速看到当前求职状态。
3. 岗位列表需要适合高频查看、筛选和更新。
4. 岗位详情页是信息沉淀中心，需要承载岗位、面试、AI 总结、Offer。
5. AI 总结展示需要结构清晰，避免大段纯文本。
6. Offer 对比页应使用表格或对比矩阵，方便横向比较。
7. 空状态要积极引导用户创建第一条记录。

## 21. 开发交接说明

开发时建议优先实现以下垂直闭环：

```text
注册登录
-> 创建岗位
-> 查看岗位列表
-> 修改岗位状态
-> 添加面试记录
-> 生成 AI 总结
-> 添加 Offer
-> 查看 Offer 对比
```

第一阶段不要优先投入复杂筛选、图表统计、拖拽看板等增强功能，应先保证主流程完整可用。

## 22. 开放问题

当前不阻塞 MVP，但后续需要确认：

1. 是否需要邮箱或手机号用于找回密码。
2. Offer 评分是否允许用户自定义权重。
3. AI 总结是否需要支持多次生成和版本历史。
4. 是否需要日历视图。
5. 是否需要导出 Excel / PDF。
6. 是否需要移动端深度适配。
